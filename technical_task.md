## 1. Введение

## 3. Назначение разработки

Разработать прототип файл‑сервера, обеспечивающий обмен текстовыми и бинарными файлами по TCP-соединению между клиентом и сервером.

## 4. Требования к программе или программному изделию

### 4.1 Требования к функциональным характеристикам
- Общение клиента с сервером должно проводиться в формате запрос-ответ. Формат запроса: **команда** \[параметры] \[контент]. Формат ответа: **код ответа** \[контент]. В клиентском приложении нужно выводить ответ. Коды ответа должны иметь соответствующее значение кодам состояний HTTP. Разделителем контента выступает пробел. Необходима обработка клиентских команд: **PUT**, **GET**, **DELETE**, **EXIT**.
	
- Доступ к файлам: Клиент может получить доступ к файлу на сервере, используя его идентификатор или имя файла. Для этого после команды GET или DELETE указать, надо ли использовать идентификатор файла или имя. Использовать BY_ID и BY_NAME в качестве ключевых слов. То же самое относится и к DELETE BY_ID и DELETE BY_NAME. Если пользователь хочет получить файл, клиентская программа должна спросить, хочет ли пользователь использовать идентификатор или имя файла. После ввода идентификатора или имени пользователю необходимо указать имя, под которым следует сохранить файл. Файл должен быть сохранен в папке .../client/data/ . Если пользователь хочет удалить файл, клиентская программа должна спросить, хочет ли пользователь использовать идентификатор или имя файла. После ввода идентификатора или имени программа должна отправить запрос на сервер.
    
- Для **PUT**: приём и сохранение файла (текста или изображения) на сервере, генерация уникального идентификатора. На сервере файл должен быть сохранен в папке .../server/data/. С запросом необходимо отправлять название, с которым файл сохранится на сервере.  Изначально на сервер отправляется команда с запросом на создание файла с заданным именем: "PUT FILE_NAME". Сервер должен создать пустой файл, сгенерировать уникальное имя для этого файла и отправить обратно положительный код при успешности. При получении положительного кода, клиент начинает загрузку файла на сервер. По завершении загрузки файла возвращается код ответа и уникальный идентификатор (при успешности). 
    
- Для **GET**: передача файла клиенту по имени или по идентификатору. Клиент отправляет запрос "GET \(BY_ID | BY_NAME) \(ID | NAME)" и указывает, с каким названием он локально хочет сохранить файл, далее ожидает ответ. Сервер обрабатывает запрос, если передан идентификатор, конвертирует его в название файла, находит файл, формирует и отправляет ответ. При положительном результате ответ включает содержимое найденного файла. При положительном ответе клиентская программа создает файл с указанным названием и записывает в него переданный сервером контент.
    
- Для **DELETE**: удаление файла по имени или идентификатору. Клиент отправляет запрос "DELETE \(BY_ID | BY_NAME) \(ID | NAME)" и ожидает ответ. Сервер обрабатывает запрос, если передан идентификатор, конвертирует его в название файла, находит и удаляет файл. При положительном результате ответ содержит лишь код ответа.
    
- Для **EXIT**: завершение работы сервера. Клиент отправляет запрос формата: EXIT. Сервер обрабатывает запрос, если возможно завершить работу, отправляет положительный ответ и прекращает работу.

### 4.2 Требования к надёжности

- Сохранение состояния (списка файлов и их идентификаторов) на диске для восстановления после перезапуска.
    
- Параллельная обработка запросов на сервере с использованием многопоточности.
    
- Защита от гонок при доступе к ресурсам (синхронизация).
    

### 4.3 Условия эксплуатации

- Операционная система: Windows или Linux.
	
- .NET 9.0
    
- Порт TCP: configurable.
    
- Минимальные требования: 1 ГБ ОЗУ, 100 МБ диск.
    

### 4.4 Требования к составу и параметрам технических средств
- Сервер: папка `server/data` для хранения файлов.
    
- Клиент: папка `client/data` для временных сохранений.
    
- Файлы разных типов — текстовые и бинарные.
    

### 4.5 Требования к информационной и программной совместимости

- Протокол передачи: TCP.
    
- Формат данных: length-prefix framing для двоичных потоков.
    
- Кодировка текста: UTF-8.
    

### 4.6 Требования к маркировке и упаковке

- Программное изделие поставляется как ZIP-архив с бинарными файлами сервера и клиента.

### 4.7 Требования к транспортированию и хранению

- Архивы хранятся согласно политике ИТ-безопасности.
    

### 4.8 Специальные требования

- CLI-интерфейс для клиента
    

## 5. Требования к программной документации

- Руководство пользователя.
    
- Описание API (формат команд и ответов).
    
- UML-диаграммы (см. приложения).
    

## 6. Технико-экономические показатели

- Ориентировочное время разработки: 2 недели.
    
- Экономия за счет автоматизированного обмена файлами.
    

## 7. Стадии и этапы разработки

**Этап 1 – Упрощённый прототип:**

1. Реализовать сервер и клиент на сокетах.
    
2. Обмен текстовыми файлами.
    
3. Обработка команд:
    
    - `PUT filename text`
        
    - `GET filename`
        
    - `DELETE filename`
        
    - `EXIT`
        
4. Сервер обрабатывает запросы последовательно.
    

**Этап 2 – Полное решение:**

1. Добавить поддержку бинарных файлов (изображений и др.).
    
2. Генерация уникального идентификатора для каждого файла.
    
3. Возможность доступаться по имени **или** по ID (`GET BY_NAME`, `GET BY_ID`, `DELETE BY_NAME`, `DELETE BY_ID`).
    
4. Реализовать многопоточный сервер для параллельной обработки клиентов.
    
5. Синхронизация доступа к ресурсам (таблица ID–имя файла сохраняется на диске).
    
6. CLI-клиент:
    
    - Запрос действия (GET, PUT, DELETE).
        
    - Выбор по имени или ID для GET/DELETE.
        
    - Запрос имени для сохранения загруженного файла.
        

## 8. Порядок контроля и приёмки

- Тестирование на параллельной нагрузке.
    
- Проверка сохранения состояния после перезапуска.
